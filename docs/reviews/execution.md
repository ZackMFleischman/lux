## Findings

### EXEC-01 — TR-05 consumes the core service that its parallel sibling creates

**Classification: implementation blocker for the advertised TR-04/TR-05 parallel execution; does not block TR-01/TR-02.**

References: [task graph and parallelism](../implementation/tracer-0.1.md), lines 51–59; TR-04 create/interfaces at lines 163–165; TR-05 interfaces/checks at lines 181–190.

The graph makes TR-04 and TR-05 independently start after TR-03 and requires each task to be tested/committed before dependent work starts. TR-05 must use core operations and run real Studio control/status/lifecycle checks, but `packages/core/src/*` and those application operations are first implemented in TR-04. Freezing runtime DTOs does not provide the missing core service. A worker following TR-05 literally must wait, introduce an unplanned mock, or create a competing operation path prohibited by B02.

Correction: make the complete TR-05 depend on TR-04, or split its independent shell/presentation construction from its core-integration acceptance. If splitting, name the interface artifact that exists before dispatch and explicitly defer real operation tests until the integrated core commit. Keep the dependency diagram and handoff consistent. An empty service interface or mock must not satisfy the TR-05 gate.

Verification: walk each TR-05 import and public operation to an already committed predecessor; its required test command must run against real operations without borrowing uncommitted sibling code.

### EXEC-02 — Identity allocation has incompatible instructions at the contract freeze

**Classification: implementation blocker for TR-03 shared schema freeze and TR-06 attachment, not for the GPU spike.**

References: [project model](../design/project-model.md), line 60; [host activation contract](../design/tracer-contracts.md), lines 38–53; [bridge](../design/resolume-bridge.md), lines 124–141.

The project model says IDs are generated by core and are opaque UUIDs. The bridge allocates a runtime-instance UUID in each native plugin object before attaching, while the contract map says to allocate an independent instance UUID on `Attach`. The same blanket UUID rule includes `ControlId`, but the canonical tracer control is the literal `intensity`. This leaves a concrete choice for schema authors and two native/core workers: validate the canonical control out of existence, or create/remap two instance IDs with unspecified reconnect semantics.

Correction: explicitly separate entity ID policy from stable declared control IDs, and name one allocator for each identity. For example, let the plugin allocate its logical instance UUID once per plugin object, include it in idempotent Attach/reconnect, and have the service validate/adopt it without replacement; core allocates authoring Scene/revision/job IDs. Alternatively use a distinct plugin-client ID and a service-returned instance UUID with a specified mapping lifetime. Update the three documents to one rule.

Verification: a duplicate Attach and reconnect retain the same logical instance; another plugin object gets a distinct one; renderer restart changes only generation; `intensity` passes the shared schema and native mapping tests.

### EXEC-03 — Fresh-frame percentage can pass a host running below the declared rate

**Classification: required before affected milestone 0.1 acceptance (TR-07); record the measurement contract before TR-02 instrumentation settles.**

References: [measurement semantics and fresh delivery gate](../implementation/tracer-acceptance.md), lines 30 and 38–47; [bridge delivery gate](../design/resolume-bridge.md), line 160.

The denominator is observed host source-consumption opportunities. There is no explicit wall-clock coverage/rate condition for those opportunities. A host configured for 60 Hz but actually invoking the source at 30 Hz for five minutes can consume a fresh frame every time, have a 33 ms gap below 100 ms, and pass the written freshness gate. The 60 Hz setting in the manifest does not establish measured delivery at that rate. This is a false-green risk even when frame IDs and CPU/GPU spans are collected correctly.

Correction: record monotonic start/end coverage and actual opportunity/delivered rates, and require the actual host cadence to match the declared 60 Hz workload within an explicit tolerance. Account for missing expected opportunities as a workload failure or a separately failed host-cadence prerequisite; never silently shrink the denominator. Keep repeat/skipped-producer counts separate and define excluded fault windows before running.

Verification: feed the acceptance calculator an otherwise perfect synthetic 30 Hz opportunity trace labeled as a 60 Hz run. It must fail workload validity. A normal five-minute trace must account for the declared elapsed window, not just its emitted callbacks.

### EXEC-04 — Control-latency sampling can omit updates that never produce an image

**Classification: required before affected milestone 0.1 control acceptance (TR-06/TR-07).**

References: [acceptance measurement semantics/control gate](../implementation/tracer-acceptance.md), lines 32 and 53; [bridge control snapshots](../design/resolume-bridge.md), lines 130–134, and automated sample stream at line 162.

Continuous updates intentionally coalesce, but the acceptance procedure does not fix stimulus cadence, minimum sample count, or treatment of received versions with no corresponding consumed frame. Computing p95/p99 only from successfully matched samples can conceal stalls or a high discarded-update fraction. For example, fast updates that disappear before rendering vanish from the latency dataset while a few surviving values look fast. Merely reporting sample count does not prevent this.

Correction: define a deterministic normal-rate latency stream with enough separated, visibly distinguishable updates to estimate p99, plus an end-of-run drain deadline. Report counts of sent, plugin-received, superseded, rendered, consumed, and unmatched updates. For the non-overload acceptance stream, an unmatched received update must fail or count as an explicit timeout, not disappear from quantiles. Test intentional high-rate coalescing separately with its own expected behavior. Specify how matching a later snapshot proves or does not prove the earlier value was visible.

Verification: remove the slowest/unmatched control response records from a fixture and confirm the report fails count reconciliation rather than improving p99. Preserve raw stimuli and receive/consume records.

### EXEC-05 — Scratch retention roots omit an explicitly activated host binding

**Classification: required before affected milestone 0.1 host activation and garbage collection (TR-04/TR-06).**

References: [project retention](../design/project-model.md), line 124; [host binding activation](../design/tracer-contracts.md), line 53; [runtime ownership](../design/runtime.md), lines 105–111.

The host design correctly says activation pins an immutable artifact, including when no host instance exists yet. The scratch retention rule nevertheless retains current, previous-working, and job-leased revisions **only**. It does not identify the binding as a retention root or say whether it retains an independent artifact/manifest closure. Activate revision A without a plugin, advance Studio to B and C, then attach the plugin: literal core collection can remove A, while the host contract still promises A. A running host may have a loaded copy, but later restart needs the artifact too.

Correction: make host bindings and live runtime recovery state explicit retention roots, or state that binding activation copies and owns the complete immutable executable/manifest closure independently of Scene revision collection. Specify release on successful replacement/service shutdown, and keep the previous bound artifact until replacement succeeds. This does not require milestone-1 durability; scratch service restart may still lose the binding as documented.

Verification: activate A before host Attach; accept B and C; force eligible scratch collection; then Attach and restart the renderer. Both must render A with host-owned values. A failed binding replacement must preserve A and its recovery bytes.

### EXEC-06 — Environment outputs use two different directory conventions

**Classification: optional documentation cleanup before handoff.**

References: [environment preflight output](../implementation/environment.md), lines 23–25; [TR-01 file targets](../implementation/tracer-0.1.md), line 65; [acceptance evidence layout](../implementation/tracer-acceptance.md), lines 7–12.

The environment guide writes `evidence/tracer-0.1/environment.json` and `preflight.md`; the task plan/evidence layout put both under `<run-id>/`. This can leave a report pointing at mutable or missing evidence, though the acceptance manifest's hash requirements reduce the risk.

Correction: use the run-scoped paths throughout, or explicitly describe the root files as pointers whose immutable targets are copied and hashed at sign-off. Verify manifest links from a fresh checkout plus the documented binary archive.

## Bounded discoveries that are not planning blockers

- Actual Electron/Three.js/FFGL/Spout versions, ABI and adapter compatibility belong to TR-01 and TR-02. The design is correct to require a recorded compatibility result rather than invent a tested tuple now.
- WebGPU worker presentation, shared-texture readiness, alpha, GL interop, compositor/frame association, callback blocking and achievable budgets are the assigned TR-02 experiment. Their uncertainty blocks downstream expansion only if the experiment fails.
- The concrete minimal `VisualContext` declarations and test-local harness helpers can be implemented in TR-03 after the chosen GPU route is known. They must be frozen before dependent core/UI work; they are not evidence that arbitrary Three.js scenes already work.
- Full Dockview packaged popout behavior, two-host composition persistence, event throughput, durable projects, graph editing and controlled replay are explicitly staged later. Requiring them for initial GPU feasibility would expand the tracer improperly.
- The handoff refers to `docs/reviews/disposition.md`, absent from this intentionally pre-review snapshot. Creating and linking the disposition is already remaining coordinator work, not evidence of a missing implementation dependency today.
