# Lux visual creation

Turn the user's visual brief into working Lux source, inspect the actual preview, and iterate from feedback. Match the requested look and movement; use creative judgment when the brief leaves room. A technical plan or a code listing alone does not complete a request to create a visual in Studio.

## Connect and inspect

Prefer available `lux.studio.*` MCP tools. Otherwise read [connection and tools](references/studio-tools.md) for the local stdio adapter. Use the existing Studio session; ordinary visual creation does not call for launching extra Studio instances, running integration tests, modifying infrastructure, or installing/exporting to Resolume.

For startup, use **start-lux**, which prefers the installed desktop build and returns its matching adapter configuration. A requested checkout uses an isolated creative profile. Use configured MCP tools only when discovery confirms the intended profile and checkout. If an older connection lacks `lux.library.*`, use the matching installed/checkout stdio adapter described in [connection and tools](references/studio-tools.md); do not infer that the library is unavailable or change global client configuration. Ordinary development launches use per-worktree profiles; tests use unique `test-*` profiles. Never select a test instance for creative work. Retain the live `studioSession.sessionId`; temporary adapters use `LUX_STUDIO_SESSION_ID` to guard that selection.

Call `discover`, then `read`. Discovery supplies the adapter checkout's SDK contract, example, allowed imports, versions, and declared capabilities; `runningStudio` separately reports the running app's capabilities and compatibility. Require compatibility for the SDK you use. Use the adapter from the checkout/build that launched the current Studio when known, and verify actual `read`, `status`, and operation results. Read returns the **complete source bundle**, draft version, and current preview status. A newer adapter can describe features absent from an already-open build; investigate that mismatch rather than trusting either this skill's snapshot or discovery alone. Do not print connection credentials.

## Create and revise

Read [visual programming](references/visual-programming.md) before the first implementation. For procedural displacement, read [noise and meaningful parameters](references/noise-and-parameters.md); its [sphere template](assets/noise-sphere.ts) illustrates a CPU-compiled starting point, not a visually approved finished design.

Before inventing a visual component, use the compact Library catalog already supplied in the MCP server instructions or `discover`. Treat each description as guidance for when that component is useful. Reuse this metadata during ordinary edits; do not call `lux.library.list` before each component or edit. Read the complete source with `lux.library.read` only for a likely match. Use `list` or `discover` to refresh after an external library change, or reconnect for a fresh initialization snapshot. `create` and `update` responses include the refreshed compact catalog. Prefer known working components and the smallest useful code edit. For a control-only change, use the current live parameter IDs and guards instead of rebuilding source. Avoid redundant discovery, rebuilds, and helper abstractions; when source must change, keep the fresh draft-version guard and verify the actual preview. Reuse a suitable entry through `build.libraryLinks` in an SDK 0.4 composition; preserve existing links when editing that scene. SDK 0.2 visuals cannot link library entries: inspect the catalog, then use scene-local source if that format better fits the brief. Choose new source when the available entries do not fit. If the matched running build lacks library support, report that limit and continue with scene-local source.

Prefer a small runnable root with nested logical components when a visual has independently useful behavior with a real supported input/output contract. Keep each part's controls on the component that owns its behavior; expose selected controls at composition boundaries instead of duplicating state. For example, a scene may keep a top-level starfield, a `Quasar` composition, and demo planets, while `Quasar` contains compatible lensing, jet, and bloom effects. This is a pattern, not a required component count. An explicit rapid-prototyping request can start scene-local; revisit boundaries as the shape stabilizes without waiting for a second request. Do not create a component for every helper or a cosmetic passthrough node merely to make the graph look reusable. Group related controls by the editing task, such as `Motion`, `Shape`, or `Color`. Use SDK 0.2 for a self-contained visual when decomposition would add no useful reuse.

Organize authored source to make the boundary legible: put a reusable component's implementation and helpers together under a clear scene or Library folder, keep the runnable root small, and name the exposed contract from its consumer's point of view. A nested component still needs an actual supported port contract; do not invent multiple image inputs, feedback links, or graph capabilities that discovery does not report.

When the request calls for reusable work, finish by considering which working parts belong in the shared Library. Explicitly `create` a new entry for an independently useful, supported component, or `read` and `update` the intended existing entry with its current `expectedRevision` when the revision should be available to all linked scenes. Each scene adopts it on load/rebuild or through **Apply update**; publishing does not immediately replace every open scene. Keep scene-specific experiments local. Studio's **Fork** UI action makes a linked component scene-local; no MCP fork tool is exposed. Give published parts clear names and descriptions, and report which entries were created or updated. Building or saving the scene does not publish them. The Library accepts independently published `image`/`paths2d`/`shader-field` leaves, including data-only generators and renderers with typed inputs, and SDK 0.4 compositions with supported typed inputs. Validation adds compile-only boundary providers/consumers as needed; stored source is unchanged. Leave source-file and graph-node capacity for that harness.

A published shader-field leaf must name a real ABI and the compatible consumers it serves, such as a 3D ray renderer reading a gravity or world-geometry field. Do not extract a shader field from a 2D postprocess merely to create another Library entry.

Keep generated and revised TypeScript readable in Studio Source. Use normal indentation, spacing, multiline metadata and controls, and one statement per line in lifecycle methods. Preserve user comments and existing behavior when formatting. A formatter is optional; do not add a formatter dependency or build step for this purpose.

For PNG, JPEG or BMP images, read [image assets](references/image-assets.md). Check the running app's `capabilities.imageFormats` and `assetExport`, not just the adapter's advertised formats. Use `context.images` for admitted decoded pixels; preserve original asset bytes in complete-source edits. The [image plane example](assets/image-plane.ts) shows texture setup and disposal.

- Preserve existing files and assets unless the requested change removes them. For Scene versions 1–6, Build replaces the **entire source bundle**, not one file or a patch; preserve `sourceVersion` and `assets` on v2 documents. For Scene 7, `read.document` is authoritative and Build replaces that **entire multi-visual document**. Treat `read.source` as the selected editor view, edit the matching `document.visuals` row, and preserve every other visual, cache, animation, setting, tempo value, and Story field.
- Submit with the `expectedDraftVersion` from the read you based the edit on. If a user or another agent has edited meanwhile, reread and merge the intended change into the latest source. Do not replay the old bundle with a newly fetched version number.
- Parameters belong to each visual's code. Use the discovered declaration/control schema; Intensity is not a required global semantic. SDK 0.2 declares number, boolean and enum `controls` directly in `defineVisual` when the running Studio reports those `parameterKinds`, with no fixed control-count ceiling (metadata byte bounds still apply); use the actual runtime schema/hash for guarded MCP patches. Legacy 0.1 retains its compatibility Intensity. If an old running app cannot use 0.2, report the mismatch. Continue the useful visual work without changing the SDK.
- Momentary actions use `type: 'trigger'` declarations and `frame.events`, never slider counters or saved values. Require running `controlTriggers` capability. Invoke the generic `lux.studio.trigger` with a discovered ID, current guards and a fresh `commandId`; retry an uncertain invocation with the same ID in the same generation. A completed-frame receipt confirms delivery. Paused triggers draw once without starting playback. See [Studio tools](references/studio-tools.md) for retry and reset semantics.
- Story-aware SDK 0.2 root visuals declare supported beats in source and consume `frame.story`; saved Story definitions give those beats labels/timing and optional sequence occurrences. Require the running app's `story` capability. A Scene 7 Story contains one to eight complete SDK 0.2 visuals; its Story v2 definition assigns visual IDs to normal, beat, and occurrence behavior. Read and rebuild the complete `document`, never only its selected `source`. Use `lux.story.read` and the generic `lux.story.transport`, keeping beat identity separate from occurrence identity. Manual launch stays indefinitely; a sequence occurrence may assign a dwell. Only timed/direct beats support local seek, replay and loop. Return to normal preserves ambient time. Read [Story playback](references/story-playback.md) before authoring or operating a Story. Successful rebuild/recovery returns to Normal; definitions persist but playback state does not. Composition Story and Resolume Story export are not supported.
- Numeric controls can declare an optional `group` label. Studio renders each named group as its own keyboard-accessible disclosure inside **Controls**, in declaration order; collapsing a group does not change its values or playback. Use short, meaningful groups when several controls form a clear editing task, such as `Shape` or `Motion`. Keep small control sets ungrouped instead of creating one-control sections. Component controls retain their group when exposed by an SDK 0.4 composition.
- SDK 0.4 uses `defineComponent` for reusable code (`metadata` and `create`) or a literal internal graph (`definitions`, `nodes`, `edges`, `output`, `expose`). A node is an instance of a component. Use `defineVisual` for the runnable root graph; the saved Scene contains its source and settings. A reusable graph component can use legacy `input: { nodeId, portId }` for one image input, or typed `inputs: { name: { nodeId, portId } }` for one or more immediate-child input ports; the two forms are mutually exclusive. Port types are inferred from those child inputs. The runnable root cannot declare external inputs. Use explicit `expose` rows. Two instances keep independent leaf controls. Patch the public aliases reported by runtime status. The flattened graph supports one or more reachable leaf components and one final image, without a fixed component-count ceiling. Source/metadata byte budgets, compilation deadlines, resource limits, and device performance still apply. Legacy image chains remain supported; explicit image, paths2d and shader-field connections can form acyclic fan-out. Feedback, delays, and interactive graph rewiring are unavailable. The [graph component](assets/component-group.ts) and [runnable visual](assets/component-visual.ts) templates wrap an existing SDK 0.4 `source.ts` image-source component with an `intensity` control; adapt that concrete control to the selected source. Existing `defineComposition` groups/roots and SDK 0.1/0.2 direct visuals remain supported without rewriting saved source. Direct visuals appear as a selectable Visual component in Graph; their controls and animations retain the existing flat scene identity.
- **Readable graph IDs:** When discovery reports `authoring.graphIds.kind: 'uuid-or-readable-v1'`, default to stable semantic node and edge IDs such as `starfield`, `quasar.disk`, and `disk-to-bloom`. Readable IDs must match `[a-z][a-z0-9._-]{0,95}`; UUIDs remain valid. IDs are unique only within their immediate graph, so use a visual namespace where it clarifies ownership and keep IDs unchanged after authoring because node/control paths and bindings depend on them. They do not replace component, library, project, scene, request, revision, or runtime-instance identities.
- **CameraController:** Use this only when discovery from the adapter paired with the running Studio reports `composition.cameraController` with ABI `lux/camera-controller/v1`, control IDs `yaw`, `pitch`, `panX`, `panY`, `dolly`, `roll`, and `studioPreviewGestures: true`. The zero-render Library leaf exposes `camera: { kind: 'shader-field', version: 1, abi: 'lux/camera-controller/v1' }` and owns those six numeric controls. A compatible 3D consumer declares the matching `camera` input and resolves `readCameraController(inputs.camera.data)` into `resolveCameraPose(authoredBase, values, { focusDistance, minDistance? })` immediately before its render or camera-uniform update. These offsets are additive and non-accumulating: angles are radians; pan and dolly are normalized by the consumer focus distance. Gestures apply only through this explicit edge with all six aliases exposed. It does not make arbitrary scenes, 2D visuals, or image postpasses camera-controllable, and it does not replace the consumer's authored camera controls.
- In Studio, use View → Open Graph to inspect an accepted visual. Graph opens inside **Scene**: the canvas shows the direct Visual or the immediate children of a composition. Scene is the enclosing workspace, not a sibling canvas node. The header has one breadcrumb trail: the current location is plain text and ancestors are clickable. Selecting a node opens its Inspector controls; clicking the canvas background returns to scene controls. Select a leaf to edit its controls, or select a composition to edit its exposed controls. **View inside**, Enter, or double-click opens a selected composition; clicking an ancestor breadcrumb navigates up and selects that container. **Alt+↑** goes up one level while Graph has focus and stays at Scene when already at the top, and **View inside** is absent when the selection cannot contain children. The Inspector resolves an exposed control and its child view to the same leaf state and local LFO. Edits preserve sibling instances and the final output selection. Drag the background to pan; use Zoom and Fit to frame the current composition. Closing and reopening Graph keeps its view and selection for the same scene when those paths still exist. Graph does not add, remove or reconnect nodes. MCP parameter writes still use exposed public aliases.
- Every declared numeric scene control (SDK 0.2, legacy 0.1, or an SDK 0.4 exposure) and selected Graph node's control can use Studio's **Animate** button for a local LFO. A separate reset button restores the declared base default. The base value stays editable and saved; the preview evaluates `base + amount × waveform` within the control's declared bounds. Period is 0.05–3600 seconds, amount is a nonnegative peak distance in the control's units, and start phase is 0–1. Play, pause and reset use the scene clock. Turning an animation off returns the base value and preserves its frozen phase; removing it deletes the binding. Save/Open preserves compatible bindings, including linked scenes. If a node/control identity or schema changes incompatibly, Studio retains the binding disabled with an issue instead of moving it to another control. Scene controls bind to their declared schema; component controls bind per node instance; it does not create shared LFOs or MIDI mappings.
- The same Inspector editor can add stable per-instance variation to one numeric control. Set a nonnegative amount as a symmetric range around the editable base and choose **Random**, **Center-weighted**, or **Spread**. Authored code opts in for each repeated element with `frame.sampleControl?.('controlId', instanceKey) ?? frame.controls.controlId`; use a stable string or whole-number key. The optional call keeps source compatible with older Studio builds. A configured binding is saved with the Scene, remains stable across frames, clamps to the control bounds, and is inspectable in runtime status. Use `lux.studio.variation` with current runtime, revision, schema, node-path, and control guards when discovery reports `controlVariation.stableInstanceKeys`; pass `variation: null` to remove it.
- The same editor can add **Tempo** modulation with sine, triangle, saw, or square shape, 0.25–64 beats per cycle, nonnegative amount, and phase 0–1. Scene BPM is manual from 20 through 300, defaults to 120, and is saved with the Scene. Set BPM or use **Tap** beside transport; accepted tap intervals are 200–2000 ms and the newest four intervals are averaged. Tempo follows the visual frame clock, freezes while paused, and returns to beat zero on Reset, reopen, or runtime restart. `lux.studio.tempo.set` and `lux.studio.tempo.tap` require current runtime/revision guards and a running Studio protocol 3 tempo capability. Tempo does not estimate BPM from audio.
- Studio's same **Animate** editor can add a continuous Level/Bass/Mids/Highs response or a detected Kick response after the user explicitly connects the shared audio input. Kick controls expose sensitivity, a retrigger interval, linear or exponential envelope shape, attack, release, and amount. They use the scene clock: pause freezes an active envelope and consumes new kicks until playback resumes; reset clears the response. Save/Open keeps portable analyzer and binding settings while the physical device choice stays local. Disconnect releases contributions to the editable manual base. Kick detection is transient response only; it does not infer BPM, expose raw audio to visual code, or imply Resolume audio parity. When the running app reports `capabilities.controlAnimation.guardedBindings`, use `lux.studio.animation` to configure or remove these bindings for any discovered numeric control; read the exact target and audio payload in [Studio tools](references/studio-tools.md). When discovery reports `capabilities.audioInputControl`, an explicitly authorized connection can use `lux.studio.audio.inputs` to select an exact device ID, then `lux.studio.audio.connect` with the shared analyzer settings. This reuses Studio permission handling; `audio.disconnect` releases capture. Never choose a physical input without user authorization. `status.audioInput` reports the connected input's availability and current bands.
- For a representative music spectrum, use the optional `frame.audioSpectrum` in SDK 0.2 visual or SDK 0.4 component `update(frame)` when the running app reports `capabilities.audioSpectrum`. It contains 128 readonly normalized FFT magnitude buckets on a logarithmic 20 Hz to Nyquist axis, not PCM or invented oscillator motion. Read `available` before using it; disconnected frames contain zeros. Pause holds the displayed spectrum and Reset clears one frame. Use [the spectrum contract and example](references/studio-tools.md#audio-spectrum-in-visual-code), and preserve a quiet fallback on older hosts.
- Standard shared components are available through `lux.library.list`, `read`, `create`, and `update` when discovery reports them; the shipped seed includes the **Prismatic Ball** image source. Checkout profiles and a desktop build made from that checkout use the same marked repository library while it is available. A standalone installed app uses the visible app-data fallback and merges nonconflicting additions and history-backed updates when its recorded repository returns. The connected create/update path accepts independent image/paths2d/shader-field leaves and SDK 0.4 compositions with supported typed inputs. `create` and `update` are explicit reusable-library operations; ordinary scene builds and saves remain local to the scene. Read a component before reuse. Pass its stable ID and a unique `mountPath` in `build.libraryLinks`; Studio resolves the latest revision and mounts the complete source bundle there. Library updates use `expectedRevision`, and running scenes show an explicit Apply update action. A fork keeps the mounted source in the scene and removes its library link. The Library panel's Copy agent request action only copies instructions; it does not insert code or send a message.
- Build the authorized creative edit, inspect diagnostics, and correct source errors. Normal Studio startup automatically builds and plays its initial visual. A successful later Build or scene Open also starts the accepted visual playing. During a background Build, the current preview keeps playing and its controls and animations remain editable; Studio applies the latest compatible acknowledged edits to the candidate before replacing the preview. A later explicit Pause during compilation or candidate startup wins before promotion. Failed builds preserve the previous working preview, edits, and playback state. A timeout or lost response is uncertain: read the actual source/status before resubmitting. Bound recovery; report a persistent service/runtime failure instead of repeatedly restarting it.

### Composing Library entries

Publish independently useful generators and renderers as separate entries. A composition can store only its wiring source and declare `dependencies: [{ componentId, revision, mountPath }]` in Library create/update. Import a dependency through that relative mount, for example `./generator/paths.ts`. Dependencies pin immutable revisions; update the composition with new dependency revisions explicitly when desired. `library.read({id, revision})` reads an exact revision; omitting revision reads latest. A linked scene resolves the dependency source into its saved fallback, so it remains reopenable if the Library becomes unavailable. Publishing a dependency alone does not silently update pinned compositions. Do not copy an implementation into another published entry just to compose it.

## Check the result

Capture the actual completed frame and inspect its composition, silhouette, palette, and visible defects. A successful compile is not a successful visual. Capture metadata identifies the revision, frame, and control state; verify it corresponds to the intended build.

Respect the user's explicit play/pause state after Build or Open completes. A paused preview can be captured immediately; waiting does not make it animate. When animation verification is needed and consistent with the user's intent, use the playback tool and inspect separated frames. Restore a pause changed only for testing. Do not substitute frame count for visual judgment.

Briefly report what changed, which controls are live versus source settings, and what was actually inspected. Save/Open, Preview frame/video capture, and export are Studio UI workflows unless discovery provides newer tools. A successful build does **not** imply the scene was saved, captured, or exported.

For failures in a matching build, read the local log path returned by `status.diagnostics` or `discover.runningStudio.diagnostics`; see the connection reference for bounded retention and privacy rules.
